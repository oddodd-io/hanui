# 블로그 계획 — B2B 대시보드 트랙 (2026-11 ~)

> [plan-2026-11.md](plan-2026-11.md) 가 전체 발행 계획의 기준이고, 이 문서는 그중 **B2B 장비 관리 대시보드**
> 소재만 따로 관리한다. 글감을 꺼낼 때 아래 표에서 다음 항목을 가져가고, 발행하면 상태를 `발행` 으로 바꾸고 슬러그를 적는다.

## 1. 방향

**지금 하고 있는 일에서 글을 뽑는다.** 주제를 먼저 정하고 자료를 찾지 않는다.

- 중심축: **수천 대 장비를 다루는 B2B 관리 대시보드를 만들면서 알아낸 것**
- 성격: 공공 CMS 트랙이 "기준(KRDS·KWCAG)을 맞추는 이야기" 라면, 이 트랙은 **"실측해서 판단을 바꾼 이야기"** 다.
  최적화를 추가한 글은 흔하고, **지운 글은 드물다.** 그 차이가 이 트랙의 자리다.
- 근거 원천: 로컬 작업 공간의 글감 원장과 작업 기록 (이 저장소 밖, push 대상 아님)
- **지어낸 수치 금지.** 모든 숫자는 실제 측정 결과에서 끌어온다. 근거가 없으면 그 글은 아직 쓸 때가 아니다.

## 2. 호칭 규칙 (반드시 지킨다)

이 트랙의 소재는 **회사 업무**다. 공개 글에는 회사명·제품명·약칭·티켓 번호·사내 경로를 쓰지 않는다.
무슨 종류의 제품인지만 서술한다. 설득력은 제품 이름이 아니라 문제의 구조에서 나온다.

| 쓰지 않음                                          | 대신                                           |
| -------------------------------------------------- | ---------------------------------------------- |
| 회사명, 제품명, 그 약칭                            | `B2B 장비 관리 대시보드`, 반복될 땐 `대시보드` |
| 사내 디자인 시스템 이름                            | `사내 디자인 시스템`                           |
| 티켓 번호, 사내 저장소 경로, API 엔드포인트·필드명 | 기능 설명으로 바꾼다 ("집계 엔드포인트")       |
| 고객·규모 수치                                     | 구간으로 ("수천 단위 장비")                    |
| 사내 화면 스크린샷                                 | 쓰지 않는다. 최소 재현 예제를 새로 만든다      |
| 동료 실명·직책                                     | 등장시키지 않는다                              |

가짜 제품명도 지어내지 않는다. 가명을 붙이면 어느 제품인지 추측 게임이 시작된다.

- 괜찮은 문장: "수천 대 장비를 다루는 B2B 대시보드에서, 상태 카운트를 병렬로 쪼갰더니 더 느렸어요."
- 안 되는 문장: 제품명·티켓 번호·사내 경로가 들어간 모든 문장

## 3. 발행 리듬 — 블록 단위로 이어서 낸다

**매 편 트랙을 섞지 않는다.** 한 시리즈를 3~4편 연속으로 내고, 블록이 끝나면 트랙을 바꾼다.
하루 1편 리듬은 전체 계획과 같다.

왜 섞지 않는가:

- **편당 초안 비용**이 가장 적게 든다. 같은 주제를 연속으로 쓰면 맥락이 남아 있어 2편째부터 체감이 줄고, 트랙을 매번 바꾸면 측정 맥락을 매번 다시 올려야 한다. 이 트랙은 반출 검사가 한 단계 더 붙어 전환 비용이 특히 크다.
- **미완 시리즈가 쌓이지 않는다.** 1편만 있고 다음 편이 없는 시리즈는 독자 신뢰를 깎는다. 완결된 시리즈 하나가 산발적인 20편보다 강하다.
- **`series`/`seriesOrder` 링크 클러스터**가 촘촘해져 한 편으로 들어온 독자가 나머지를 이어 읽는다.

규칙:

1. **열려 있는 시리즈를 먼저 닫는다.** 새 트랙을 열기 전에 진행 중 시리즈의 남은 편을 본다.
2. 블록 사이에 **단독으로 완결되는 글 1편**을 쉬어가기로 끼울 수 있다 (시리즈 흐름을 끊지 않으므로).
3. 큐에 3편 이상 쌓인 상태를 유지한다. 3편 미만이면 원장에서 보충하고, 근거 부족한 건 `보류` 로 내린다.

### 이 트랙을 꺼내도 되는 조건

소재의 **`버린 길`과 `수치·근거`가 채워져 있을 때만** 꺼낸다.

원장 항목 중 사후에 캐낸 것들은 이 두 칸이 비어 있다 — 작업 당시의 과정이 남아 있지 않기 때문이다.
비어 있으면 **작업 기록이 쌓일 때까지 꺼내지 않는다.** 없는 과정을 지어내지 않는다.

예외는 폐기 판단이 문서로 남아 있는 트랙 A 1편(`parallel-chunking-removed`)이다 — 폐기 사유·버린 길·측정 결론이 그대로 있어 지금 써도 완성도가 나온다.

### 발행 순서 (2026-11 기준)

| 순서 | 블록                                                      | 상태                        |
| ---- | --------------------------------------------------------- | --------------------------- |
| 1    | 진행 중인 공공 CMS·KRDS 시리즈의 남은 편 (전체 계획 참조) | 먼저 닫는다                 |
| 2    | **쉬어가기 1편 — 트랙 A 1편** `parallel-chunking-removed` | 단독 완결, 근거 확보됨      |
| 3    | 공공 CMS·KRDS 다음 블록                                   |                             |
| 4    | **트랙 A 블록** (성능 실측 3편)                           | 이때까지 작업 기록을 쌓는다 |
| 5    | 트랙 B 블록 (접근성·리팩터 판단 3편)                      |                             |
| 6    | 트랙 C 블록 (규칙 자동화 3편)                             |                             |

트랙 D(단독 글)는 블록 사이 쉬어가기 자리에 하나씩 꺼낸다.

## 5. 글 한 편의 꼴

공공 CMS 트랙과 같은 구조를 쓰되, 이 트랙은 **수치가 먼저** 온다.

1. 사건 — 무엇을 하다가 무엇이 어긋났나 (재현 조건 포함)
2. 실측 — Before 수치. 무슨 도구로 어떻게 쟀는지
3. 원인 — 왜 그랬나 (코드 최소 예제 하나)
4. 버린 길 — 검토했다가 쓰지 않은 방법과 이유 ← **이 트랙의 핵심**
5. 결과 — After 수치, 또는 "그래서 지웠다"
6. 오늘 정리 3줄 + 관련 링크 + 시리즈
