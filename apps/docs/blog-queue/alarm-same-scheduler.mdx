"블로그 글 1개 남았대."

이 말을 듣고 큐를 열었어요. 정말 1편이었습니다. 내일 나가면 **큐가 빕니다.**

그래서 코드를 봤어요. 큐가 비면 알림이 오는지 확인하려고요. 감시 라우트와 날짜 판정 모듈을 읽었습니다.

```js
export function findOverdue(entries, today) {
  return entries.filter((e) => e.date && e.date < today).sort(/* … */);
}
```

밀린 글만 찾습니다. 큐가 비면 밀린 글이 0편이니까 아무것도 안 열려요.

그래서 이렇게 보고했습니다. **"큐가 비면 아무 알람도 안 울립니다."** 그리고 그 전제로 기능을 만들기 시작했어요.

틀렸습니다.

## 이미 있었어요

재고 알람은 **처음부터 있었습니다.** 발행 워크플로 안에요. 라벨은 `blog-restock`, 기준 3편, 열고 갱신하고 닫는 것까지 다 돼 있었어요.

더 민망한 건 큐 폴더 README 11번째 줄에 이렇게 적혀 있었다는 거예요.

> 남은 예약글이 3편 미만이면 "재고 부족" GitHub 이슈로 알려줍니다.

**그 줄을 읽고도 넘겼습니다.** "내가 안 만들었으니 없겠지"로요.

왜 못 봤냐면, **감시 코드만 보고 발행 코드를 안 열었어요.** 이 시스템은 발행(GitHub Actions)과 감시(Vercel Cron)가 일부러 두 곳에 나뉘어 있습니다. 그런데 저는 한쪽만 읽고 "전체에 없다"고 단정했어요.

기능이 두 곳에 나뉘어 있으면, **한쪽에 없다는 건 전체에 없다는 뜻이 아닙니다.**

## 그런데 구멍은 진짜 있었어요

알람은 있는데, **발행 워크플로 안에 있습니다.** 워크플로가 돌 때만 돌아요.

[지난 글](/blog/publish-redundancy-interval)에 적었던 그 날을 다시 보면 — 11월 16일에 예약 두 번이 모두 건너뛰어졌을 때, **발행만 빠진 게 아니라 재고 감시도 같이 쉬었습니다.**

이 프로젝트에는 이미 원칙이 하나 있었어요. 부재 감시를 Vercel Cron으로 옮기면서 주석에 박아둔 문장입니다.

> 그 감시를 같은 GitHub Actions cron에 올리면 같은 이유로 같이 죽으므로, 완전히 다른 스케줄러에서 본다.

**이 원칙을 부재 감시에만 적용하고 재고 감시에는 빠뜨렸어요.**

그러니까 구멍은 "알람이 없다"가 아니라 **"알람이 감시 대상과 같이 죽는다"**였습니다. 제가 틀린 건 진단이고, 고칠 게 있다는 건 맞았어요. 다만 고칠 곳이 달랐습니다.

## 새 라벨을 만들 뻔했어요

처음엔 `blog-queue-low`라는 새 라벨로 짰습니다. 기존 걸 못 봤으니까요.

알고 나서도 잠깐 고민했어요. 그냥 둘까? 안 됩니다. **같은 조건에 이슈가 둘로 갈라지면, 한쪽을 닫아도 다른 쪽이 남아요.** 글을 써서 재고를 채웠는데 알람이 계속 울리는 꼴이 됩니다.

답은 이미 코드 안에 있었어요. 부재 알람은 워크플로(늦음)와 Vercel(부재)이 **같은 `blog-publish-missed` 이슈**를 씁니다. 스케줄러는 둘인데 이슈는 하나예요.

규칙으로 정리하면 이렇습니다.

- **뜻이 같으면** 스케줄러가 달라도 **라벨을 공유**한다 → 둘 다 `blog-restock`
- **뜻이 다르면** 나눈다 → 부재(`blog-publish-missed`) vs 재고(`blog-restock`)

제목도 글자까지 맞췄어요. 같은 이슈를 둘이 쓰는데 제목 형식이 다르면 **돌 때마다 서로 제목을 되돌립니다.**

## 덤으로 나온 진짜 결함

두 감시가 같은 이슈를 쓰기로 했으니, **같은 숫자를 세는지** 봐야 했어요. 보니까 안 그랬습니다.

워크플로 쪽 재고 계산이 이랬어요.

```js
const remaining = fs.readdirSync(QUEUE_DIR).filter((f) => f.endsWith('.mdx')).length;
```

**큐 폴더의 파일 개수**입니다. 그런데 `date` 프론트매터가 없는 글은 발행 스크립트가 건너뛰어요. 큐에 영원히 남습니다. 그 글들이 재고로 세어지고 있었어요.

합성 큐로 확인했습니다. 발행 가능한 글 2편 + 날짜 없는 글 1편을 넣고 양쪽을 돌렸어요.

```
예전 코드:  남은 예약글 3편              low_stock=false
지금 코드:  남은 예약글 2편 — ⚠️ 재고 부족  low_stock=true
```

**날짜 없는 글 하나가 알람을 막고 있었습니다.** 재고는 2편인데 3편이라고 세서, 기준(3편 미만)에 안 걸렸어요.

고친 건 간단해요. 파일 수가 아니라 **앞으로 나갈 편수**를 셉니다. 그리고 두 감시가 **같은 모듈의 같은 함수**를 씁니다. 따로 세면 같은 이슈에 번갈아 다른 숫자를 적게 되니까요.

## 하나 더: 제목이 비어 나간 커밋

작업하다 발행 커밋 목록에서 이걸 봤어요.

```
publish: 예약 글 1편 발행 (남은 4편) —
```

대시 뒤가 비어 있습니다. 글 제목이 들어가야 할 자리예요.

프론트매터를 읽는 함수가 이렇게 생겼었어요.

```js
new RegExp(`^${field}:\\s*['"]?([^'"\\n]+)['"]?\\s*$`, 'm');
```

값을 `[^'"\n]+`로 잡습니다. **따옴표를 못 들어가게** 해놨어요. 그런데 그날 발행된 글 제목이 이거였습니다.

```yaml
title: 'axe가 "판단 불가"로 남긴 661곳을 직접 계산했어요 — 명도 대비 3.08:1의 발견'
```

제목 안에 큰따옴표가 있어요. 매칭이 통째로 실패하고 빈 문자열이 돌아갑니다.

감싼 따옴표만 벗기고 **안쪽은 건드리지 않도록** 고쳤어요. 글 75편을 전부 훑어 제목 못 읽는 글이 0편인 것까지 확인했습니다.

커밋 제목이 비는 건 사소해 보이는데, 저 커밋 제목은 **"남은 N편"을 눈에 보이게 하려고** 일부러 넣은 거였어요. 알림을 놓쳐도 커밋 목록에서 재고가 보이라고요. 그 장치가 반쯤 깨져 있었습니다.

## 반대 의견

**"코드를 더 꼼꼼히 읽었으면 될 일 아닌가요?"**

맞아요. 그런데 "더 꼼꼼히"는 다음에도 똑같이 실패합니다. 제가 가져가는 건 이거예요 — **"X가 없다"고 말하기 전에 X를 하는 다른 경로가 있는지 먼저 센다.** 발행과 감시가 두 곳에 나뉜 걸 알고 있었으면서 한쪽만 읽은 게 문제였습니다.

**"알람을 두 곳에서 돌리면 중복 아닌가요?"**

같은 이슈를 쓰면 아니에요. 둘 중 **먼저 도는 쪽이 열고, 나중에 도는 쪽이 갱신**합니다. 재고가 회복되면 어느 쪽이든 닫아요. 알림은 한 번만 옵니다.

## 오늘 정리

1. **기능이 두 곳에 나뉜 시스템에서 한쪽만 보고 "없다"고 단정하면 틀립니다.** 없다고 말하기 전에 경로를 세어보세요.
2. **감시는 감시 대상과 다른 곳에서 돌아야 해요.** 부재 감시에는 적용했는데 재고 감시에는 빠뜨렸습니다. 원칙은 한 번 세우면 끝이 아니라, 같은 모양의 코드마다 다시 확인해야 합니다.
3. **"몇 편 남았나"를 파일 수로 세지 마세요.** 나갈 수 없는 파일이 재고를 부풀려 알람을 막습니다.

본인 프로젝트에서 확인해보실 거라면 이걸 해보세요. **알람의 임계값에 쓰는 숫자가 "세기 쉬운 것"인지 "실제로 중요한 것"인지 보세요.** 파일 개수·행 개수·레코드 개수는 세기 쉬워서 자주 쓰이는데, 그중 몇 개가 쓸모없는지는 안 세집니다.
