공공 CMS에서 기관 로고를 바꾸려고 SVG를 올렸어요. **안 받아졌습니다.**

코드를 보니 막아둔 게 분명했어요. 허용 목록에 `svg`가 없고, 본문 정리기도 `svg`를 내용째 지웁니다. 의도적입니다.

그런데 **왜 막았는지가 어디에도 안 적혀 있었어요.** 결정 기록에 SVG 관련 항목이 0건. "요즘 SVG 많이 쓰는데 왜 안 돼?"라는 질문에 답하려고 **코드를 읽어 역산**해야 했습니다.

이 글은 그 역산의 기록이고, 겸사겸사 "열려면 뭘 해야 하는가"까지 정리한 거예요.

## 허용 목록은 이렇게 생겼어요

```ts
export const ALLOWED_EXTENSIONS: Record<FileKind, string[]> = {
  image: ['png', 'jpg', 'jpeg', 'webp', 'gif'],
  document: ['pdf', 'hwp', 'hwpx', 'docx', 'xlsx'],
};
```

이미지 5종, 문서 5종. `svg`는 없어요.

그런데 허용 목록만으로는 "왜"가 안 보입니다. 옆에 있는 함수를 보고 나서야 알았어요.

## 이유 ① 검사할 서명이 없습니다

이 제품은 **확장자를 안 믿어요.** 파일 내용의 머리 바이트를 봅니다.

```ts
const SIGNATURES: Record<string, (b: Uint8Array) => boolean> = {
  png:  (b) => [0x89, 0x50, 0x4e, 0x47, 0x0d, 0x0a, 0x1a, 0x0a].every((v, i) => b[i] === v),
  jpg:  (b) => b[0] === 0xff && b[1] === 0xd8 && b[2] === 0xff,
  webp: (b) => String.fromCharCode(...b.slice(0, 4)) === 'RIFF' && String.fromCharCode(...b.slice(8, 12)) === 'WEBP',
  gif:  (b) => ['GIF87a', 'GIF89a'].includes(String.fromCharCode(...b.slice(0, 6))),
  pdf:  (b) => String.fromCharCode(...b.slice(0, 5)) === '%PDF-',
  hwp:  (b) => [0xd0, 0xcf, 0x11, 0xe0, 0xa1, 0xb1, 0x1a, 0xe1].every((v, i) => b[i] === v),
  ...
};
```

```ts
if (!matches) return '등록할 수 없는 파일 형식입니다.';
return matches(head) ? null : `파일 내용이 ${ext.toUpperCase()} 형식이 아닙니다. 확장자만 바꾼 파일은 올릴 수 없습니다.`;
```

**허용 목록의 10종 전부가 고유한 머리 바이트를 가집니다.** 실행 파일 이름을 `.pdf`로 바꿔 올려도 `%PDF-`가 아니라서 걸려요.

SVG는요? **텍스트입니다.** 검사할 서명이 없어요.

`<svg`로 시작하는지 보면 되지 않냐고 할 수 있는데, 그건 서명이 아니라 **문자열 검사**예요. 앞에 공백이나 XML 선언이나 주석을 넣으면 됩니다. 바이너리 형식의 머리 바이트처럼 "이 형식이면 반드시 이 값"인 게 아니에요.

그러니까 SVG를 받으면 **이 제품의 검사 원칙에 예외가 하나 생깁니다.** 그게 첫 번째 이유였어요.

## 이유 ② SVG는 이미지가 아니라 실행되는 XML이에요

이게 더 큽니다.

PNG는 아무리 이상하게 만들어도 그려질 뿐이에요. SVG는 다릅니다. **`<script>`가 들어가고, 이벤트 속성이 붙고, 외부 자원을 불러올 수 있어요.** 브라우저가 SVG를 열면 그 스크립트가 실행됩니다.

그리고 업로드한 이미지는 **같은 출처에서 `inline`으로 내려갑니다.** 담당자가 올린 SVG를 방문자가 열면, **그 사이트의 출처에서 남의 스크립트가 도는** 거예요. 저장형 XSS입니다.

공공 사이트에서 이게 왜 특히 나쁘냐면, **올리는 사람이 반드시 믿을 수 있는 건 아니기** 때문이에요. 기관 담당자 계정이 털릴 수도 있고, 여러 부서가 같은 CMS를 쓰기도 합니다.

## 열어주는 세 가지 길을 비교했어요

바로 구현하지 않고 셋을 놓고 봤습니다.

| 안 | 내용 | 결과 |
| --- | --- | --- |
| ① **저장 시점 정화** | 업로드할 때 `script`·이벤트·외부 참조를 씻어낸다 | **채택 (미구현)** |
| ② 별도 도메인 | 업로드 파일을 다른 출처에서 서빙한다 | 탈락 |
| ③ CSP 헤더 | `Content-Security-Policy`로 스크립트 실행을 막는다 | 단독으로는 부족 |

**② 별도 도메인을 버린 이유**가 이 제품에서 결정적이었어요. 업로드 파일을 다른 출처로 빼면 스크립트가 돌아도 본 사이트를 못 건드립니다. 정석이에요.

그런데 **기관마다 도메인을 하나 더 받고 인증서를 하나 더 발급**해야 합니다. 이 제품은 **폐쇄망에 Docker로 설치**하는 모델이에요. 설치 설명서가 "도메인 두 개와 인증서 두 장을 준비하세요"로 시작하면, 그건 다른 제품입니다.

**③ CSP가 단독으로 부족한 이유**는 두 가지예요. 헤더가 도착해야만 방어되는데 **기관 앞단 프록시를 우리가 통제하지 못합니다.** 그리고 헤더가 잘 붙어도 **저장된 파일 자체는 여전히 악성**이에요. 백업에, 다른 경로로 내려받을 때 따라갑니다.

**① 정화를 고른 이유**는 비용이 생각보다 낮아서였습니다. [3편](/blog/rules-node-sidecar)에서 쓴 구조 덕분이에요.

> 정화 규칙은 TS에 한 번 쓰면 **화면과 백엔드가 같이 씁니다.**

본문 HTML을 허용 목록으로 정리하는 기존 원칙과 **완전히 같은 모양**이에요. 새 개념이 안 늘어납니다. 그리고 헤더와 무관하게 안전해요 — 씻어서 저장하니까요.

## 그런데 아직 안 만들었어요

정직하게 적으면 **채택했지만 구현은 미뤘습니다.**

추정한 범위는 이래요. **반나절~하루, 건드릴 곳 6군데** — TS 규칙, file-policy 양쪽, 정답 예제, OpenAPI + 계약 테스트, `FileController`, mock 서버.

미룬 이유는 **아직 실제로 필요한 사례가 없어서**예요. 기관이 SVG 로고만 들고 오는 경우가 확인되면 그때 만듭니다. 안 쓰일지 모르는 예외를 보안 경계에 미리 뚫어둘 이유가 없어요.

대신 **열 때 생기는 비용**은 적어뒀습니다.

- 머리 바이트 서명 검사 원칙에 **예외가 생깁니다.** GS 심사에서 설명해야 해요
- 정화를 Node 도우미가 하므로 **도우미가 죽으면 로고 업로드도 503**이 됩니다(본문 저장과 같음)
- 로고 한 자리에만 열지, 본문 이미지까지 열지 **범위를 정해야** 해요

## 진짜 교훈은 다른 데 있었어요

이 글의 출발점은 "SVG가 왜 안 되지?"였는데, 쓰고 나니 문제는 그게 아니었습니다.

**결정이 코드에만 있었어요.** 허용 목록에 `svg`가 없는 것, 본문 정리기가 `svg`를 지우는 것 — 둘 다 분명한 의도인데, **그 의도가 기록되지 않았습니다.**

그래서 제가 코드를 읽고 역산해야 했어요. 저는 이 코드를 아는 사람인데도요. **다음 사람은 "빼먹었나 보다" 하고 그냥 추가할 겁니다.** 보안 결정이 그렇게 조용히 풀려요.

막는 코드는 왜 막는지를 안 적으면 **누가 언제든 풀 수 있는 코드**가 됩니다. 허용 목록 옆에 한 줄만 있었으면 이 글을 쓸 일도 없었을 거예요.

## 오늘 정리

1. **SVG는 이미지 취급을 받는 실행 파일이에요.** 다른 이미지 형식과 같은 칸에 두면 안 됩니다.
2. **설치 모델이 보안 설계를 제한합니다.** 별도 도메인은 정석인데, 폐쇄망 Docker 납품에서는 설치 난이도가 올라가서 못 씁니다. 정답은 환경에 달려 있어요.
3. **막는 결정은 반드시 적어두세요.** 코드에만 있으면 다음 사람이 "빠뜨린 것"으로 보고 풀어버립니다.

본인 프로젝트에 업로드 기능이 있다면 하나만 확인해보세요. **허용 목록에 svg가 있는지, 있다면 그 파일을 어떤 헤더로 내려주는지.** `Content-Disposition`이 `inline`이고 같은 출처면 확인이 필요한 상태예요.
