접근성 도구를 찾아보면 이런 이름들이 쏟아집니다.

```
axe-core   axe DevTools   Accessibility Insights   WAVE   Lighthouse
jsx-a11y   vitest-axe   addon-a11y   pa11y
```

저도 한참 헷갈렸어요. 특히 **`a11y`라는 이름이 여기저기 붙어 있어서** 더 그렇습니다. 브라우저 탭에도, Storybook 패널에도, ESLint 플러그인 이름에도 들어가요. 그 글자만 보고는 뭐가 뭔지 구분이 안 됩니다.

정리하고 나니 간단했어요. **속은 거의 같고, 껍데기와 도는 시점이 다릅니다.**

> 확인 시점 2026-11-23. 도구 설명은 각 공식 문서 기준이고, 가격·등급은 문서에 안 적힌 게 많아 여기 쓰지 않았습니다.

## 먼저: 엔진은 대부분 하나예요

이름이 달라도 안에서 검사하는 건 **axe-core** 하나인 경우가 많습니다.

- **axe-core** — Deque가 만든 검사 엔진입니다. npm 패키지이고 라이선스는 MPL-2.0. WCAG 2.0·2.1·2.2의 A/AA/AAA 규칙과 모범 사례 규칙을 씁니다
- **Accessibility Insights**의 자동 검사도 문서에 *powered by axe-core*라고 적혀 있어요
- **Lighthouse**의 접근성 항목도 axe-core를 씁니다

그래서 **"어느 도구가 더 많이 잡느냐"로 고르는 건 대체로 의미가 없어요.** 같은 엔진이니까요.

고를 기준은 다른 겁니다. **언제, 어디서 도는가.**

## 세 칸으로 나눕니다

| 칸 | 언제 | 누가 보나 |
| --- | --- | --- |
| **브라우저에 설치** | 화면을 보고 있을 때 | 사람이 직접 |
| **프로젝트에 설치** | 코드를 쓰고 테스트할 때 | 자동, 매번 |
| **밤에 돌리기** | 아무도 안 볼 때 | 자동, 쌓임 |

---

## 1. 브라우저에 설치 — 지금 이 화면을 보며

**이럴 때 좋아요:** 화면 하나를 깊게 볼 때. 왜 이게 걸리는지 요소를 짚어가며 확인할 때.

### axe DevTools 확장

크롬 웹스토어에서 설치합니다. 개발자도구에 탭이 하나 생겨요.

- 무료로 쓸 수 있고, **Intelligent Guided Tests(IGT)**가 들어 있습니다 — 자동으로 못 정하는 걸 사람에게 물어가며 판정하게 돕는 기능이에요
- 결과가 **위반(violations)**과 **직접 봐야 하는 것**으로 나뉘어 나옵니다

### Accessibility Insights for Web

마이크로소프트가 만들었고 크롬·엣지용 확장입니다. **오픈소스**예요(`microsoft/accessibility-insights-web`).

구성이 특이해서 저는 이쪽이 더 유용했어요. 두 가지 모드가 있습니다.

**FastPass** — 5분 안에 흔하고 영향 큰 것만 봅니다. 세 단계예요.

1. **자동 검사** (axe-core)
2. **Tab stops** — Tab을 눌러가며 초점 순서를 직접 확인합니다. 화면에 경로가 그려져요
3. **Needs review** — 자동이 "모르겠다"고 한 것을 사람이 판정합니다

**Assessment** — WCAG 2.1 AA 전체를 훑습니다. **수동 테스트 약 20개**에 단계별 지침이 붙어 있어요.

2번 **Tab stops가 특히 좋습니다.** 초점이 어디로 가는지 눈으로 보이거든요. 이건 자동 검사가 대신해줄 수 없는 종류예요.

### 크롬 기본 기능 (설치 없이)

확장을 깔기 전에 이미 있는 것도 있어요.

- **Elements → Accessibility 패널** — 선택한 요소의 접근성 트리, 계산된 이름, ARIA 속성이 보입니다
- **Lighthouse 탭** — 접근성 점수를 냅니다. 다만 axe-core 규칙을 **전부 돌리지는 않아요**

## 2. 프로젝트에 설치 — 코드를 쓰면서

**이럴 때 좋아요:** 같은 실수를 반복하지 않게 막을 때. 사람이 기억 안 해도 걸리게 하고 싶을 때.

제가 실제로 쓰는 구성입니다.

```
eslint-plugin-jsx-a11y      쓰는 순간      에디터에 빨간 줄
vitest-axe + axe-core       테스트 돌릴 때  컴포넌트 단위 검사
@storybook/addon-a11y       컴포넌트 보며  스토리마다 패널에 결과
@axe-core/playwright        화면 전체      실제 브라우저로 검사
```

단계가 다른 게 핵심이에요. **왼쪽일수록 빨리 걸리고, 오른쪽일수록 진짜에 가깝습니다.**

`jsx-a11y`는 **코드를 보고** 판단해서 즉시 알려주지만, 실행해봐야 아는 건 못 잡아요. `@axe-core/playwright`는 **진짜 브라우저에서 진짜 DOM**을 보니 정확한데, 느리고 서버를 띄워야 합니다.

컴포넌트 테스트에 한 줄 넣는 건 이 정도예요.

```ts
it('axe 위반이 없다 (팝업 열림 포함)', async () => {
  // 컴포넌트를 마운트하고 axe를 돌린다
});
```

**스토리북 애드온은 과소평가돼 있어요.** 컴포넌트를 만들면서 바로 옆 패널에 결과가 뜨니까, 고치는 비용이 제일 쌉니다. 다 만들고 나서 찾으면 되돌리기 어려워요.

---

## 3. 밤에 돌리기 — 아무도 안 볼 때

**이럴 때 좋아요:** 화면이 수십 개라 매번 못 돌릴 때. "어제보다 나빠졌는지"만 알고 싶을 때.

여기서 쓰는 건 2번과 **같은 도구**입니다. 다른 건 **언제 돌리고 결과를 어떻게 다루느냐**예요.

제 공공 CMS 쪽은 이렇게 해뒀어요.

```
pnpm a11y            화면 36개 × PC(1440px)·좁은 화면(320px)
pnpm a11y:keyboard   키보드 흐름 22개
```

한 번 돌리면 **보고서 파일**이 날짜별로 남습니다. 핵심은 점수가 아니라 **기준선(baseline)**이에요.

> 0을 목표로 하지 않고, **어제 숫자보다 늘었는지**만 본다.

처음부터 0으로 만들려면 영영 못 시작해요. 지금 숫자를 적어두고 **그보다 늘면 막는** 쪽이 현실적입니다.

**정직하게 적으면 저는 아직 CI에 안 붙였습니다.** 손으로 돌리고 있어요. 붙여야 할 일로 남겨뒀습니다.

## 자동이 안 잡는 게 생각보다 많아요

이게 이 글에서 제일 하고 싶은 말입니다.

axe-core 문서에 이렇게 적혀 있어요.

> axe-core로 **평균 57%의 WCAG 문제를 자동으로** 찾을 수 있다.

절반 조금 넘습니다. (제품 소개 쪽에는 "최대 80%"라는 수치도 있는데, **엔진 문서의 57%와는 다른 출처의 주장**이라 같이 쓰면 안 돼요.)

제 경우를 보면 체감이 됩니다. 화면 36개를 돌렸더니 이랬어요.

```
위반: 0건
```

**완벽해 보였죠.** 그런데 axe는 판단 못 한 것을 `incomplete`라는 칸에 따로 적어둡니다. 거기 있던 661곳을 직접 계산했더니 **34곳이 기준 미달**이었어요. ([그 이야기는 따로 썼습니다](/blog/contrast-661-manual))

그러니까 **`violations: 0`은 "통과"가 아니라 "자동으로 확인된 범위에서 통과"예요.**

자동이 못 잡는 대표적인 것들입니다.

- **초점이 어디 있는지** — 보이지 않는 곳으로 가도 "요소가 존재"하면 통과예요
- **화면낭독기가 실제로 뭐라고 읽는지**
- **대체 텍스트가 말이 되는지** — 있기만 하면 통과입니다
- **순서가 논리적인지**

그래서 좋은 도구들이 **"사람이 확인할 것"을 따로 안내**해요. Accessibility Insights의 Needs review·Manual tests, axe DevTools의 IGT가 그 자리입니다. 그 기능이 있는 도구를 고르는 게 낫습니다.

## 처음이면 이 순서로

하나씩 늘리는 걸 권합니다. 한 번에 다 넣으면 경고가 쏟아져서 전부 끄게 돼요.

1. **`eslint-plugin-jsx-a11y`** — 설치가 제일 쉽고 즉시 효과가 보입니다
2. **Accessibility Insights FastPass** — 주요 화면 몇 개에 5분씩. 특히 **Tab stops**
3. **컴포넌트 테스트에 axe** — 공용 컴포넌트부터
4. **화면 전체 검사 + 기준선** — 여기까지 오면 CI에 붙입니다

**2번을 건너뛰지 마세요.** 1·3·4는 전부 자동이라 같은 57% 안에서 놉니다. 2번이 나머지를 보는 유일한 자리예요.

## 오늘 정리

1. **대부분 같은 엔진(axe-core)이에요.** "뭐가 더 잘 잡나"가 아니라 **언제 도는가**로 고르세요.
2. **세 칸으로 나누면 정리됩니다** — 브라우저에 설치(보면서) · 프로젝트에 설치(쓰면서) · 밤에 돌리기(쌓이면서).
3. **`violations: 0`은 통과가 아니에요.** 자동은 평균 57%고, 판단 못 한 칸(`incomplete`)과 사람이 볼 항목이 따로 있습니다.

지금 당장 하나만 해보실 거라면 **Accessibility Insights를 깔고 FastPass의 Tab stops**를 돌려보세요. 본인 화면에서 초점이 어떻게 돌아다니는지 보이는데, 그게 제일 충격적입니다.
