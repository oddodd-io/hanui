설정 화면에 토글이 있어요. 켜면 저장되고 끄면 저장됩니다. 흔하죠.

그런데 **빠르게 두 번 누르면** 가끔 이상해집니다. 껐는데 잠시 뒤 다시 켜져 있어요. 새로고침하면 켜진 상태고요.

가끔이라서 더 나쁩니다. **재현이 안 되면 고칠 수가 없어요.**

## 재현부터 만들었어요

버그를 눈으로 쫓는 대신 **확률을 재기로** 했습니다. 서버 왕복을 흉내 내고, 왕복 시간만 매번 다르게 줬어요.

```js
let server = false;                       // 서버의 진짜 값
const save = (v, ms) => new Promise((r) => setTimeout(() => { server = v; r(v); }, ms));

// 왕복 시간은 매번 다르다 (네트워크·서버 부하)
const latency = () => 20 + Math.floor(Math.random() * 60);
```

그리고 흔히 짜는 방식 — **누를 때마다 바로 보낸다.**

```js
async function naive(clicks) {
  server = false; let ui = false;
  const sent = clicks.map((v) => { ui = v; return save(v, latency()); });
  await Promise.all(sent);
  return { ui, server };
}
```

**켰다가 바로 끄기**(`[true, false]`)를 1000번 돌리고, 끝난 뒤 **화면과 서버가 같은지**만 봤습니다.

```
① 바로 보내기: 1000번 중 화면≠서버 475번 (47.5%)
```

**절반 가까이 틀립니다.** "가끔"이 아니었어요.

## 왜 절반인가

생각해보면 당연합니다. 요청 두 개가 겹쳐 있고 왕복 시간이 무작위예요.

```
누름:  켜기 ──────────────▶ (55ms)
       끄기 ───────▶ (31ms)
```

**끄기가 먼저 도착하고, 켜기가 나중에 도착합니다.** 서버에 마지막으로 남는 값은 "켜짐"이에요. 화면은 "꺼짐"을 보여주고 있고요.

왕복 시간이 무작위니까 **어느 쪽이 먼저 도착할지는 동전 던지기**입니다. 그래서 47.5%예요. 50%에 가까운 게 오히려 정상이에요.

이게 왜 그동안 안 보였냐면, **보통은 천천히 누르기** 때문입니다. 앞 요청이 끝난 뒤에 누르면 겹칠 일이 없어요. 겹치게 만들려면 연타해야 하는데, 그건 **실수로 두 번 누르거나 반응이 없어서 다시 누를 때** 일어납니다. 즉 **사용자가 불안할 때만** 생기는 버그예요.

## 고친 건 세 줄

앞 요청이 끝나야 다음을 보냅니다.

```js
async function serialized(clicks) {
  server = false; let ui = false; let chain = Promise.resolve();
  for (const v of clicks) { ui = v; chain = chain.then(() => save(v, latency())); }
  await chain;
  return { ui, server };
}
```

`chain`에 계속 이어 붙이는 게 전부예요. 같은 조건으로 다시 1000번.

```
① 바로 보내기: 1000번 중 화면≠서버 475번 (47.5%)
② 직렬화:      1000번 중 화면≠서버   0번 (0.0%)
```

**0번입니다.**

## 왜 "마지막 요청만 보내기"가 아닌가

처음엔 디바운스를 떠올렸어요. 300ms 기다렸다가 마지막 값만 보내면 겹칠 일이 없죠.

**안 골랐습니다.** 두 가지 때문이에요.

**첫째, 한 번만 누른 사람도 300ms를 기다립니다.** 연타는 드문 경우인데 그 대가를 모두가 치러요. 토글은 즉시 반응해야 하는 컨트롤입니다.

**둘째, 중간 상태가 사라집니다.** 켜기 → 끄기 → 켜기를 눌렀는데 마지막 "켜기"만 보내면, 서버의 변경 기록에는 **아무 일도 없었던 게** 됩니다. 감사 기록이 중요한 제품이면 이게 문제예요.

직렬화는 **다 보내되 순서를 지킵니다.** 느리지만 정확해요.

그리고 솔직히, **디바운스로 못 막습니다.** 300ms보다 느린 요청이 하나라도 있으면 다음 요청과 겹쳐요. 디바운스는 요청 수를 줄이는 거지 순서를 보장하지 않습니다.

## 그래도 남는 것

직렬화해도 **화면은 여전히 먼저 바뀝니다.** 낙관적 업데이트니까요.

마지막 요청이 **실패하면** 화면과 서버가 또 갈라집니다. 그건 직렬화가 아니라 **실패 처리**의 몫이에요 — 되돌리거나, 다시 시도하거나, 사용자에게 알리거나.

직렬화가 막는 건 **"둘 다 성공했는데 결과가 틀린 경우"** 하나입니다. 그게 제일 찾기 어려운 종류라서 먼저 막았어요.

## 오늘 정리

1. **가끔 생기는 버그는 확률을 재세요.** "가끔"인 줄 알았는데 47.5%였습니다. 숫자가 나오면 고칠 가치가 분명해져요.
2. **겹친 요청은 응답 순서가 보장되지 않아요.** 늦게 보낸 게 먼저 도착하면 먼저 보낸 값이 최종값이 됩니다.
3. **디바운스는 순서를 보장하지 않아요.** 요청 수를 줄일 뿐입니다. 순서가 중요하면 직렬화하세요.

본인 제품에서 확인하실 거라면 **토글을 아주 빠르게 두 번 누르고 새로고침**해보세요. 상태가 돌아와 있으면 같은 문제입니다.
