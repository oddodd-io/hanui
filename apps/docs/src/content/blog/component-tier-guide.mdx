컴포넌트 라이브러리를 만들다 보면 반드시 이 순간이 옵니다.

**"이거 어디에 넣지?"**

로그인 폼을 만든다고 해봐요. 버튼·입력칸을 조합한 거니까 컴포넌트인가요? 아니면 더 큰 단위인가요? 폼 제출 로직이 들어가면 달라지나요?

세어보니 Component 78 · Block 42 · Kit 8, 합쳐서 128개였습니다. **128번 고민했다는 뜻이고, 매번 답이 같지 않았어요.**

## AI가 다섯 번째를 만들어요

혼자 할 때는 그럭저럭 굴러갑니다. 기준이 머릿속에 있으니까요.

AI와 작업하면 다릅니다. "로그인 폼 만들어줘"라고 하면 **있는 걸 찾아 쓰는 대신 새로 만듭니다.** 기존 것과 비슷하지만 미묘하게 다른 걸요.

왜냐면 **"어디에 있어야 하는지"를 모르기 때문**이에요. 사람은 "로그인 폼이면 블록이겠네" 하고 그 폴더부터 봅니다. 기준이 없으면 찾을 자리를 모르니 그냥 만들어요.

그래서 비슷한 게 네 개가 되고, 다섯 번째가 생깁니다. **한 번 네 개가 되면 어느 걸 써야 할지 사람도 몰라요.**

## 세 칸으로 나눴어요

기준을 문서에 박았습니다. 핵심은 **"무엇으로 나누는가"**였어요.

처음엔 **크기**로 나누려 했습니다. 작으면 컴포넌트, 크면 블록. **안 됐어요.** 테이블은 큰데 컴포넌트고, 빈 상태 안내는 작은데 블록입니다.

그래서 **의존성과 상태**로 나눴습니다.

| | Component | Block | Kit |
| --- | --- | --- | --- |
| 파일 | 단일 | 단일 | **폴더** |
| 다른 컴포넌트 import | 안 함 | **함** | 함 |
| 상태 | 없음 (부모가) | 로컬(`useState`) | **전역 + 서버** |
| 비즈니스 로직 | 없음 | 가벼움 | **API·캐싱·검증** |
| 예 | Button, Table | LoginForm, EmptyState | Board Kit |

**판정이 한 줄로 끝납니다.**

- 다른 컴포넌트를 가져다 쓰나? → 아니면 **Component**
- API를 부르거나 전역 상태를 쓰나? → 쓰면 **Kit**
- 둘 다 아니면 → **Block**

크기나 느낌이 아니라 **코드를 보면 바로 답이 나오는** 기준이에요. 판정에 취향이 들어가면 사람마다 달라지니까요.

## 가장 유용했던 건 "하지 마라"

표보다 효과가 컸던 게 각 칸의 **금지 사항**입니다.

```
Component: 상태 없음. 비즈니스 로직 없음. 순수 프레젠테이션
Block:     로컬 상태만 (useState). forwardRef 미사용
Kit:       폴더 구조 (types/api/hooks/store/components 분리)
```

왜 금지가 더 유용했냐면, **애매한 걸 밀어내기** 때문이에요.

컴포넌트에 `useState`를 넣고 싶어지는 순간이 옵니다. "이 정도는 괜찮지 않나" 싶죠. 금지가 적혀 있으면 **거기서 멈추고 "그럼 이건 블록인가?"를 묻게** 됩니다. 그 질문이 분류를 지켜줘요.

금지가 없으면 컴포넌트가 조금씩 블록이 되고, 블록이 조금씩 킷이 됩니다. **경계는 한 번에 무너지지 않고 한 줄씩 무너져요.**

여기까지가 **기준을 만든 이야기**입니다. 잘 굴러갔어요. 그런데.

## 그리고 11개월 뒤, 한 칸을 버렸습니다

첫 Kit을 만든 게 2025-12-13, 내린 게 2026-11-23입니다. **Kit을 내렸어요.** 문서에서도, 레지스트리에서도, 패키지 export에서도.

```
레지스트리  before  ui 65 · block 28 · kit 8
            after   ui 65 · block 28
```

이유가 셋이었습니다.

**1. 아무도 안 썼어요.** 공개 사이트도 관리자 화면도 전부 Component와 Block으로 만들어져 있었습니다. Kit을 쓴 화면이 **하나도 없었어요.** 만든 사람조차 안 쓴 겁니다.

**2. 설치가 깨져 있었어요.** 레지스트리에 등록은 돼 있는데 실제로 받아보면 안 됐습니다. **아무도 안 쓰니까 깨진 줄도 몰랐죠.**

**3. 의존성을 강요했어요.** Kit 하나를 쓰면 axios·React Query·Zustand·React Hook Form·Zod가 따라옵니다. "컴포넌트 하나 가져다 쓰려는" 사람에게는 너무 큰 요구예요.

**소스는 지웠나?** 안 지웠습니다. `packages/react/src/kits`에 남겼어요. 그리고 `/kits` 주소도 안내 페이지로 남겼습니다 — **이미 발행한 글이 그 주소를 링크하고 있어서**, 지우면 그 글의 링크가 죽거든요.

## 버리고 나서 보인 것

분류 기준 자체는 틀리지 않았어요. **Kit이라는 칸의 정의는 정확했습니다** — 폴더 구조, 전역 상태, API 포함. 판정도 잘 됐고요.

틀린 건 **그 칸이 필요하다고 가정한 것**이었습니다.

생각해보면 신호가 처음부터 있었어요. 세 칸 중 **Kit만 예외가 붙어 있었거든요.** 위치가 두 군데(`src/kits`와 `src/components/kits`)였고, 글에도 "원래는 하나여야 한다"고 적어뒀었습니다.

**예외가 붙는 칸은 잘 안 쓰이는 칸일 수 있어요.** 자주 쓰면 불편해서 벌써 고쳤을 테니까요. 예외를 적어두는 건 좋은 습관인데, **적어둔 예외가 한 칸에만 몰려 있으면 그건 다른 신호**입니다.

## 오늘 정리

1. **크기로 나누지 마세요.** 큰 컴포넌트도 있고 작은 블록도 있습니다. **의존성과 상태**로 나누면 코드를 보고 판정할 수 있어요.
2. **금지 사항이 표보다 유용해요.** "상태 없음"이 적혀 있으면 애매한 게 스스로 다음 칸으로 밀려납니다.
3. **칸을 만들었으면 쓰이는지도 세세요.** 정의가 정확해도 아무도 안 쓰면 유지 비용만 남습니다. 저희는 그걸 11개월 뒤에 알았어요.

비슷한 컴포넌트가 셋 이상 있다면 지금이 기준을 적을 때예요. 그리고 **반년 뒤에 각 칸이 실제로 몇 번 쓰였는지 한 번 세어보세요.** 0인 칸이 있을지도 모릅니다.
