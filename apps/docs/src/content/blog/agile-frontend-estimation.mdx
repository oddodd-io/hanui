"이 화면 얼마나 걸려요?"

"이틀이요."

그리고 닷새가 걸려요. 매번요.

20년 동안 이 대화를 수백 번 했어요. 흥미로운 건 **틀리는 방향이 항상 같다는 점**이에요. 프론트엔드 추정은 넉넉하게 잡았다가 남는 경우가 거의 없어요. 항상 모자라요.

한쪽으로만 틀리면 그건 실력 문제가 아니에요. **세는 방법이 잘못된 거예요.**

## 우리는 해피 패스만 세고 있어요

"사용자 목록 화면"을 추정한다고 해볼게요. 머릿속에 뭐가 그려지나요?

테이블이 있고, 데이터가 차 있고, 검색창이 있고, 페이지네이션이 있는 화면이요. 그거 만드는 데 이틀. 맞아요, 이틀이면 돼요.

근데 실제로 만들어야 하는 건 이거예요.

| 상태 | 화면 |
|---|---|
| 로딩 중 | 스켈레톤? 스피너? 테이블 자리는 유지되나? |
| 데이터 있음 | ← **우리가 추정한 건 여기 하나** |
| 데이터 0건 | 빈 상태 문구, 일러스트, "등록하기" 유도 |
| 검색 결과 0건 | 빈 상태와 **다른 문구** ("검색어를 확인해주세요") |
| 에러 | 재시도 버튼, 문의 안내 |
| 권한 없음 | 목록은 보이는데 수정 버튼만 없음? 화면 전체 차단? |

여섯 개예요. 그중 하나만 세고 이틀이라고 답한 거예요.

여기에 더해요.

- 이름이 40자인 사용자가 있으면 테이블이 깨지나요?
- 모바일에서 테이블은 어떻게 되나요? 가로 스크롤? 카드로 전환?
- 검색 중에 페이지를 넘기면 검색어가 유지되나요?
- 뒤로 가기를 누르면 스크롤 위치가 돌아오나요?

**닷새는 추정이 틀린 게 아니라, 원래 닷새짜리 일이었어요.** 이틀은 여섯 상태 중 하나에 대한 정직한 추정이었고요.

## 프론트엔드가 유독 심한 이유

백엔드도 추정이 틀려요. 근데 프론트엔드가 더 심해요. 세 가지 이유가 있어요.

**1. 완료 기준이 눈에 보여요**

API는 스펙대로 응답하면 끝이에요. 화면은 "다 됐다"고 말한 순간부터 사람들이 봐요. 기획자가 보고, 디자이너가 보고, QA가 보고, 대표님이 봐요. 그리고 각자 한마디씩 해요. 이 피드백 루프가 추정에는 안 들어가 있어요.

**2. 남의 일정에 묶여 있어요**

API가 안 나왔고, 디자인이 확정 안 됐고, 카피가 미정이에요. 프론트엔드는 파이프라인 맨 끝이라 앞에서 밀린 게 전부 여기로 모여요. [1편](/blog/agile-ui-dev-wireframe)에서 이 병목을 어떻게 푸는지 얘기했지만, 그래도 의존은 남아요.

**3. "화면 하나"라는 단위가 거짓말이에요**

화면 하나 안에 컴포넌트가 대여섯 개 들어 있어요. 그중 뭐가 이미 있고 뭐가 새로 만들어야 하는지 모르면, "화면 하나"는 아무 정보도 없는 단위예요. [2편](/blog/agile-component-first)에서 컴포넌트 인벤토리 얘기를 한 이유가 이거예요.

## 상태 단위로 세면 정확해져요

해결책은 의외로 단순해요. **화면을 세지 말고 상태를 세요.**

```
❌ "사용자 목록 화면" — 2일

✅ 사용자 목록 화면
   - 테이블 조립 (DataTable 있음)      0.5일
   - 검색/필터 연동 (SearchBar 있음)    0.5일
   - 로딩 스켈레톤                      0.5일
   - 빈 상태 2종 (최초/검색결과)         0.5일
   - 에러 + 권한 분기                   1일
   - 모바일 대응                        1일
   ─────────────────────────────────
                                       4일
```

같은 화면인데 4일이 나와요. 그리고 이 4일은 **깎으려면 어디를 깎을지 대화가 되는 숫자**예요. "모바일은 다음 스프린트로" 하면 3일이에요. "2일에 해주세요"보다 훨씬 생산적인 대화죠.

처음엔 이게 번거로워요. 근데 화면 서너 개만 이렇게 쪼개보면 감이 잡혀서, 나중엔 머릿속에서 바로 계산돼요.

## 컴포넌트 재고를 알면 절반이 사라져요

위 추정에서 `DataTable 있음`, `SearchBar 있음`이라고 적었어요. 이게 핵심이에요.

같은 화면인데 재고 상황에 따라 이렇게 달라져요.

| 상황 | 추정 |
|---|---|
| DataTable·SearchBar·Pagination 다 있음 | 조립 1일 + 상태 처리 2일 = **3일** |
| DataTable을 새로 만들어야 함 | 위 + 컴포넌트 3일 = **6일** |
| 디자인 시스템 자체가 없음 | 색/간격부터 정해야 함 = **모름** |

**"이 화면 얼마나 걸려요?"에 답하려면 재고를 먼저 알아야 해요.** 재고를 모르면 추정이 아니라 점을 치는 거예요.

그래서 [2편](/blog/agile-component-first)의 컴포넌트 인벤토리가 추정 정확도에 바로 영향을 줘요. 인벤토리가 있으면 "이 화면에 신규 컴포넌트 1개, 나머지는 조립"이라고 말할 수 있고, 그건 꽤 정확해요.

## 모르는 건 모른다고 숫자에 넣기

가장 많이 틀리는 건 **아직 안 정해진 것**이에요. 그런데 우리는 그걸 추정에 안 넣어요. "일단 되겠지" 하고 넘겨요.

이렇게 보고하면 달라져요.

```
사용자 목록 화면

확정된 작업        3일
─────────────────────────
미확정 2건
  · 권한별 노출 정책 (기획 미정)     +0.5 ~ +2일
  · 엑셀 다운로드 포함 여부 (미정)    +0 ~ +2일
─────────────────────────
3일 (최선) ~ 7일 (전부 포함)
```

이게 "5일이요"보다 나은 이유는 정확해서가 아니에요. **공을 넘기기 때문**이에요.

기획자가 이 표를 보면 두 개를 오늘 정해줘요. 그러면 추정이 3.5일로 확정돼요. "5일이요"라고 하면 아무도 아무것도 정하지 않고, 5일 뒤에 "권한 정책이 아직인데요"라는 대화가 시작돼요.

**추정이 하는 진짜 일은 미래를 맞히는 게 아니라, 지금 뭘 모르는지 드러내는 거예요.**

## 실측을 기록하면 다음이 쉬워져요

스프린트 끝날 때 30분만 써서 이것만 적어둬요.

| 화면 | 추정 | 실제 | 차이 원인 |
|---|---|---|---|
| 사용자 목록 | 2일 | 5일 | 빈 상태·에러 안 셈, 권한 분기 추가 |
| 게시판 작성 | 3일 | 3일 | — |
| 대시보드 | 2일 | 6일 | 차트 컴포넌트 신규 |

두세 스프린트만 쌓이면 **내 팀의 배수**가 보여요. "우리는 신규 컴포넌트가 낀 화면에서 2배 틀린다" 같은 게요. 그러면 다음 추정에 그냥 반영하면 돼요.

이걸 회고에서 "왜 늦었나"로 다루면 서로 방어적이 돼요. 원인 칸에 감정 빼고 사실만 적는 게 중요해요. 누가 늦었는지가 아니라 **뭘 안 셌는지**를 찾는 자리니까요.

## 정리

1. **프론트엔드 추정은 항상 한쪽으로 틀린다** — 실력이 아니라 세는 방법 문제
2. **해피 패스 하나만 세고 있다** — 로딩·빈 상태·검색 0건·에러·권한까지 세면 숫자가 맞기 시작한다
3. **재고를 모르면 추정이 아니라 점이다** — 컴포넌트 인벤토리가 추정 정확도를 결정한다
4. **미확정은 범위로 보고한다** — 추정의 목적은 예측이 아니라 결정 요청이다

"이 화면 얼마나 걸려요?"에 바로 답하지 마세요. **"상태가 몇 개예요?"라고 되물으면**, 그 순간부터 추정이 맞기 시작해요.
