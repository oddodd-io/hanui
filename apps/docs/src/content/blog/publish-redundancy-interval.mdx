11월 17일 아침, 글이 안 올라와 있었어요.

GitHub Actions 탭을 열었습니다. 빨간 X를 찾으려고요. 그런데 **빨간 X가 없었어요.** 그날 실행 자체가 목록에 없었습니다.

실패한 게 아니라 **아예 안 돌았어요.**

## 무엇을 하는 워크플로였나

이 블로그는 글을 미리 써서 큐에 쟁여둡니다. `apps/docs/blog-queue/`에 넣고 프론트매터 `date`에 원하는 발행일을 적어두면, 매일 도는 워크플로가 오늘 날짜가 된 글을 `content/blog/`로 옮기고 커밋합니다. 푸시되면 Vercel이 배포하고 글이 올라와요.

GitHub Actions의 `schedule`을 씁니다.

```yaml
on:
  schedule:
    - cron: '19 15 * * *' # 00:19 KST — 본 실행
    - cron: '19 17 * * *' # 02:41 KST — 예비 실행
```

두 번 돌립니다. 하나가 밀려도 다른 하나가 따라잡으라고요. **이중화를 해뒀다고 생각했어요.**

## 스케줄러는 늦습니다. 그건 알고 있었어요

GitHub Actions의 예약 실행은 적어둔 시각에 안 돕니다. 그건 문서에도 적혀 있고, 저도 겪어서 재고 있었어요.

예약 시각과 실제 실행 시각 차이를 적어둔 게 이렇습니다. (UTC 기준)

| 날짜  | 본 실행 (15:19Z) | 예비 실행 (17:41Z) |
| ----- | ---------------- | ------------------ |
| 11-13 | 21:26 (+6h07m)   | 22:52 (+5h11m)     |
| 11-14 | 19:57 (+4h38m)   | 21:40 (+3h59m)     |
| 11-15 | 20:25 (+5h06m)   | 22:05 (+4h24m)     |
| 11-16 | **없음**         | **없음**           |

11-13부터 사흘은 네 시간에서 여섯 시간씩 밀렸어요. 늦긴 해도 돌긴 돕니다. 그래서 **"늦는 것"에만 대비하고 있었어요.**

11-16은 다릅니다. 늦은 게 아니라 **둘 다 없습니다.**

## 왜 둘이 같이 죽었나

워크플로는 `active` 상태였어요. "저장소가 60일 동안 조용하면 예약을 멈춘다"는 그 규칙에 걸린 것도 아닙니다 — 그 시간대 전후로 푸시가 네 번 있었어요.

GitHub이 그 구간의 예약 작업을 그냥 버린 겁니다.

문제는 제가 **두 실행을 2시간 22분 간격으로 붙여 뒀다는 것**이에요. 00:19 KST와 02:41 KST. 사흘 전에 "지연을 피하자"며 둘 다 새벽으로 당겨뒀거든요.

스케줄러가 한 시간대를 통째로 버리면, **그 안에 몰려 있는 예약은 같이 죽습니다.**

이중화의 전제는 "둘이 독립적으로 실패한다"예요. 같은 창 안에 넣으면 그 전제가 깨집니다. **좁은 창에 몰아 넣은 이중화는 이중화가 아니에요.**

## 버린 길: 예약을 더 늘리기

제일 먼저 떠오른 게 이거였어요. 두 번이 다 죽었으니 세 번, 네 번 돌리자.

안 됩니다. 같은 새벽 구간에 더 쌓으면 **같이 죽는 건 그대로**예요. 네 개를 한 바구니에 더 담는 것뿐입니다.

**수를 늘리는 문제가 아니라 거리를 벌리는 문제**였어요.

## 고친 것: 12시간

```yaml
- cron: '19 15 * * *' # 15:19 UTC = 00:19 KST — 본 실행
- cron: '19 3 * * *' # 03:19 UTC = 12:19 KST — 대체 실행
```

간격을 12시간으로 벌렸습니다. 숫자를 정하기 전에 검산을 했어요.

이 스크립트는 날짜를 **KST 달력일**로 판정합니다. `date <= today`인 글만 옮겨요. 그래서 두 실행이 **같은 KST 날짜 안에** 떨어져야 합니다. 대체 실행이 날짜를 넘기려면 11시간 41분이 밀려야 해요.

당길 수 있는 바닥은 00:00 KST입니다. 그보다 일찍 돌면 스크립트가 '어제'로 보고 오늘 글을 안 올려요. 그래서 앞쪽은 00:19, 뒤쪽은 12:19가 상한에 가깝습니다.

그때 관측 최대 지연이 +6h07m이었으니 **여유 5시간 34분**. 넉넉하다고 적어뒀어요.

## 그 여유가 다음 날 깨졌어요

11-17 대체 실행이 **+8시간 45분** 밀렸습니다.

관측 최대치가 이렇게 움직였어요.

```
+5h27m (11-13) → +6h07m (11-15) → +8h45m (11-17)
```

**볼수록 커지고 있어요.** 여유 5h34m은 이제 **2h56m**입니다.

여기서 또 시각을 당기고 싶어졌는데, 안 했습니다. 관측 하나마다 일정을 흔드는 건 "수를 늘리기"와 같은 반사예요. 여유가 아직 양수고, 음수가 되면 그때 옮기면 됩니다.

대신 cron 주석에 이 문장을 박아뒀어요.

> 지연 상한을 가정하는 계산은 다시 깨질 수 있다고 보고 읽어야 한다.

**상한이 얼마인지가 아니라, 상한을 모른다는 사실을 설계에 넣는 쪽**이 맞다고 봤습니다.

## 그래서 더 중요한 걸 놓치고 있었어요

간격을 벌려도 **두 시간대가 같이 버려지는 날은 또 옵니다.** 확률을 낮춘 거지 없앤 게 아니에요.

진짜 문제는 따로 있었습니다. 11-17에 글이 안 올라온 걸, **제가 눈으로 보고 알았어요.**

실패하면 알림이 옵니다. 그런데 **실행이 아예 없으면 알림이 안 와요.** 없는 실행은 실패하지도 않으니까요.

그래서 감시를 따로 붙였는데, 그건 다음 글에서 쓸게요. 핵심만 적으면 — 감시를 **발행과 같은 스케줄러에 올리면** 스케줄러가 죽는 날 감시도 같이 조용히 죽습니다.

## 반대 의견

**"외부 스케줄러를 쓰면 되잖아요."**

맞습니다. 서버 cron이나 Cloudflare Workers로 옮기면 GitHub 스케줄러에 안 매달려요. 다만 저장소 하나 발행하려고 운영할 것을 늘리는 거라, GitHub 안에서 거리를 벌려 먼저 재보기로 했어요. 효과가 없으면 그때 옮깁니다.

**"놓친 글은 사라진 건가요?"**

아니요. 스크립트가 `date <= today`로 비교하니까 다음 성공 실행이 밀린 글을 전부 따라잡습니다. 대신 **그날 두 편이 한꺼번에 나가요.** 유실이 아니라 뭉침이 증상입니다.

## 오늘 정리

1. **예약 실행은 늦기도 하지만 아예 안 생기기도 해요.** 늦는 것만 대비하면 절반만 대비한 겁니다.
2. **이중화는 거리 문제예요.** 2시간 22분 안에 둘을 넣으면 한 번에 같이 죽습니다. 수를 늘려도 같은 창 안이면 똑같아요.
3. **지연 상한은 관측할수록 커집니다.** 상한을 가정한 계산은 깨진다고 보고, 상한을 모른다는 걸 설계에 넣으세요.

본인 저장소에서 확인해보실 거라면 하나만 해보세요.

```bash
gh run list --workflow=<워크플로>.yml --limit 30
```

**빨간 X를 찾지 말고, 날짜가 비어 있는지 보세요.** 실패는 눈에 띄지만 부재는 안 띕니다.
