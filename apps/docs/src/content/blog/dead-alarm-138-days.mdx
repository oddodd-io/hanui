예약 큐가 비었는지 확인하려고 폴더를 열었어요. **0편**이었습니다.

그런데 재고 부족 알림이 안 와 있었어요. 재고가 3편 밑으로 떨어지면 GitHub 이슈로 알려주게 해뒀는데요.

이슈 목록을 열었습니다. 있긴 있었어요.

> **#108 📝 블로그 예약글 재고 부족 (남은 0편)** — opened on Jul 1

**7월 1일.** 그날 열려서 11월 16일까지 그대로 있었습니다. 그리고 그게 알람이 안 울린 **이유**였어요.

## 세 줄이 알람을 막고 있었어요

워크플로의 알림 단계는 이렇게 생겼었습니다.

```bash
EXISTING=$(gh issue list --state open --label blog-restock --json number --jq 'length')
if [ "$EXISTING" -gt 0 ]; then
  echo "이미 열린 이슈가 있다. 건너뜀."
  exit 0
fi
gh issue create --title "..." --label blog-restock --body "..."
```

읽으면 멀쩡해 보여요. **중복 이슈를 막으려는 코드**입니다. 매일 돌면서 매일 새 이슈를 열면 안 되니까요.

그런데 이 코드의 뜻을 풀어 쓰면 이렇게 됩니다.

> 열린 이슈가 하나라도 있으면, **아무것도 하지 않는다.**

사람이 그 이슈를 한 번 안 닫으면 그 뒤로 영영 아무것도 안 합니다. 7월 1일에 열린 #108이 닫히지 않았고, 그래서 **7월 2일부터 11월 16일까지 138일 동안** 이 단계는 매일 돌면서 매일 `exit 0`만 했어요.

제목에 박힌 "남은 0편"도 **7월 수치**입니다. 그 사이 재고가 5편으로 늘었다가 다시 0이 돼도 제목은 안 바뀌었어요. 이슈가 "지금 상태"가 아니라 "7월 1일의 상태"를 들고 멈춰 있었습니다.

## 왜 눈치채기 어려웠나

열린 이슈가 **있었기** 때문이에요.

이슈 목록을 열면 `📝 블로그 예약글 재고 부족`이 보입니다. 알람이 울리고 있는 것처럼 보여요. 실제로는 7월에 한 번 울린 소리가 멈추지 않고 있는 거였는데요.

알람이 **꺼져 있으면** 조용해서 이상한데, **켜진 채 멈춰 있으면** 정상처럼 보입니다. 이게 더 나빠요.

## 고친 것: 조건 실행을 없앴어요

가장 큰 변화는 `if:`를 떼어낸 겁니다. 예전엔 재고가 부족할 때만 이 단계가 돌았는데, 이제 **항상 돕니다.** 그리고 안에서 세 갈래로 나눴어요.

| 지금 상태        | 열린 이슈 | 하는 일                          |
| ---------------- | --------- | -------------------------------- |
| 재고 부족        | 없음      | 이슈를 **연다**                  |
| 재고 부족        | 있음      | 제목·본문을 **현재 편수로 갱신** |
| 재고 회복(3편+)  | 있음      | 댓글 남기고 **자동으로 닫는다**  |
| 재고 회복        | 없음      | 아무것도 안 함                   |

핵심은 세 번째 줄이에요. **사람이 닫지 않아도 스스로 닫습니다.**

이게 되면 "열린 이슈가 있다"는 게 비로소 **"지금 부족하다"**를 뜻하게 돼요. 예전엔 "언젠가 한 번 부족했다"를 뜻했습니다.

두 번째 줄도 같이 중요해요. 부족한 동안 **매일 현재 편수로 갱신**합니다. 이슈를 열어보면 오늘 재고가 적혀 있어요. 갱신이 없으면 내용이 썩어서 언제 얘긴지 알 수 없게 됩니다 — #108이 딱 그랬죠.

## 버린 길

**① 매번 새 이슈 열기**

중복 걱정을 없애는 제일 단순한 방법이에요. 그런데 매일 하나씩 쌓입니다. 원래 중복을 막으려고 넣은 코드가 원인이었는데, 같은 문제로 되돌아가는 셈이에요.

**② 이슈 대신 메일·슬랙으로 보내기**

알림이 눈에 더 잘 띄긴 합니다. 그런데 저장소에 웹훅 URL이나 토큰을 둬야 해요. 2026년 10월에 저장소의 비밀값을 전부 걷어내고 npm 배포도 OIDC(Trusted Publishing)로 바꿨는데, 그 원칙을 되돌리게 됩니다.

지금 방식은 `github.token`만 씁니다. 워크플로가 자기 저장소에 이슈를 여는 데 쓰는 기본 토큰이라 따로 보관할 게 없어요. **원칙 안에 있는 쪽**을 골랐습니다.

## 반대 의견

**"이슈를 자동으로 닫으면 사람이 못 보고 지나치지 않나요?"**

그럴 수 있어요. 그래서 닫기 전에 댓글로 "재고가 N편으로 회복돼 자동으로 닫습니다"를 남깁니다. 닫힌 이슈도 기록은 남아요.

반대로 **안 닫으면 어떻게 되는지는 이미 봤습니다.** 138일이었어요. 사람이 닫아야만 다음 알람이 오는 구조보다는, 자동으로 닫고 다시 여는 쪽이 낫다고 봤어요.

**"재고 3편이 기준인 게 맞나요?"**

글 한 편 쓰는 데 하루는 걸린다고 보고 사흘 여유로 잡았어요. 0편이 되고 나서 알리면 이미 끊긴 뒤입니다. 숫자 자체는 프로젝트마다 다를 거예요 — **"알아차린 뒤에 복구할 시간"**이 기준이면 됩니다.

## 오늘 정리

1. **중복을 막는 코드가 알림을 막습니다.** "이미 있으면 건너뛴다"는 "사람이 치울 때까지 아무것도 안 한다"와 같은 말이에요.
2. **알람은 꺼진 것보다 켜진 채 멈춘 게 더 위험해요.** 목록에 떠 있어서 정상처럼 보입니다.
3. **알람에는 닫는 길이 있어야 합니다.** 여는 코드만 있고 닫는 코드가 없으면, 한 번 울린 뒤로 영영 안 울려요.

본인 저장소에서 확인해보실 거라면 이걸 해보세요.

```bash
gh issue list --state open --label <알림라벨> --json number,title,createdAt
```

**열린 알림 이슈의 `createdAt`을 보세요.** 한 달이 넘었으면 그 알람은 지금 울리고 있는 게 아니라 그때 울린 채 멈춰 있는 겁니다.
