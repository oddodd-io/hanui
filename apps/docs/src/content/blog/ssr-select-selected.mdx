공공기관 게시판에 분류 필터를 붙였어요. "채용", "입찰", "일반" 중에 고르고 검색을 누르면 그 분류만 보이는 평범한 기능이에요.

동작은 맞았어요. "채용"을 고르고 검색하면 채용 글만 나왔습니다. 그런데 **선택 상자는 "전체"로 돌아가 있었어요.** 잠깐 그랬다가 제대로 바뀌는 것도 아니고, 느린 연결에서는 꽤 오래 그랬습니다.

결과는 "채용"인데 화면은 "전체"라고 말하는 상태예요. 사용자 입장에선 필터가 안 먹은 것처럼 보입니다.

## 왜 GET 폼이었나

먼저 이 화면이 왜 이렇게 생겼는지부터요. 공개 사이트의 검색 폼은 이렇게 생겼어요.

```vue
<form class="cms-board-search" method="get" :action="searchAction" role="search">
  <FormField v-if="hasCategories" label="분류" class="cms-board-search-category">
    <Select name="category" :model-value="category" :options="categoryOptions" size="medium" />
  </FormField>
  <FormField label="제목 검색" class="cms-board-search-field">
    <Input name="q" :model-value="query" size="medium" maxlength="100" />
  </FormField>
  <Button type="submit" size="medium" variant="secondary">검색</Button>
</form>
```

`method="get"`인 평범한 폼이에요. JS로 가로채서 비동기로 쏘지 않습니다. 이렇게 한 이유는 두 가지예요.

1. **JS 없이도 동작해야 해요.** 공공 사이트는 사용자 환경을 고를 수 없어요.
2. **검색 결과에 주소가 있어야 해요.** 분류·검색어가 쿼리스트링에 남으니, 결과 화면을 북마크하고 공유하고 뒤로 가기로 돌아올 수 있습니다.

그래서 검색하면 서버가 그 조건으로 그린 HTML을 새로 돌려줘요. Nuxt SSR이 담당합니다. **선택 상자의 현재 값도 당연히 그 HTML에 들어 있어야 해요.**

그런데 안 들어 있었습니다.

## 바로 옆 입력창은 멀쩡했어요

제일 이상한 건 이거였어요. 같은 폼 안에서 **제목 검색 입력창은 값이 남아 있었습니다.** `q=안내`로 검색하면 입력창에 "안내"가 그대로 있어요. 선택 상자만 초기화된 것처럼 보였습니다.

둘 다 똑같이 `:model-value`로 값을 받는데 왜 한쪽만 될까요. Vue SSR이 실제로 뭘 출력하는지 찍어봤어요.

```js
import { createSSRApp, h } from 'vue';
import { renderToString } from 'vue/server-renderer';

const html = await renderToString(
  createSSRApp({
    render: () =>
      h('div', [
        h('input', { value: 'hello' }),
        h('select', { value: 'b' }, [
          h('option', { value: 'a' }, 'A'),
          h('option', { value: 'b' }, 'B'),
        ]),
      ]),
  })
);
console.log(html);
```

결과예요.

```html
<div>
  <input value="hello" />
  <select value="b">
    <option value="a">A</option>
    <option value="b">B</option>
  </select>
</div>
```

`input`에는 `value="hello"`가 붙었고, `select`에도 `value="b"`가 붙어 있어요. 둘 다 잘 나온 것처럼 보이죠.

**문제는 `<select value="b">`가 아무 의미 없는 속성이라는 거예요.**

HTML 명세에 `select` 요소의 `value` 속성은 없어요. 브라우저는 그 글자를 그냥 무시합니다. 선택 상태를 HTML로 말하는 방법은 하나뿐이에요 — **`option`에 붙는 `selected`.**

```html
<!-- 브라우저가 알아듣는 것 -->
<select>
  <option value="a">A</option>
  <option value="b" selected>B</option>
</select>
```

`input`의 `value`는 진짜 HTML 속성이라 서버가 보낸 그대로 화면에 반영돼요. `select`의 `value`는 **DOM 속성(property)**이라서 JS가 실행된 뒤에야 존재합니다. 그래서 JS 실행 전에는 브라우저 기본 동작대로 **첫 번째 option**이 선택돼 보여요. 우리 폼에서는 그 첫 번째가 "전체"였습니다.

여기까지 오면 왜 "잠깐 깜빡"이 아니라 "꽤 오래"였는지도 설명돼요. 하이드레이션이 끝나야 고쳐지는 거니까, 느린 연결일수록 틀린 화면이 길게 보입니다. 그리고 **JS를 아예 끄면 끝까지 틀려 있어요.** GET 폼으로 JS 없이도 되게 만들어 놨는데, 정작 화면이 거짓말을 하는 상태였죠.

## 고친 것

`option`마다 `selected`를 붙였어요.

```vue
<option
  v-if="placeholder !== undefined"
  value=""
  :disabled="isRequired"
  :selected="modelValue === ''"
>
  {{ placeholder }}
</option>
<template v-if="options">
  <option
    v-for="option in options"
    :key="option.value"
    :value="option.value"
    :disabled="option.disabled"
    :selected="option.value === modelValue"
  >
    {{ option.label }}
  </option>
</template>
```

컴포넌트 주석에도 이유를 남겼습니다. 나중에 이 줄을 보고 "이거 왜 있지?" 하면서 지우면 같은 문제가 돌아오니까요.

```
option마다 selected를 붙여 서버 렌더링(SSR) HTML에도 선택 상태가 들어가게 한다
(select의 value는 DOM 속성이라 HTML에 남지 않아, JS 실행 전에는 첫 option이 선택돼 보인다).
```

## 테스트는 SSR로 써야 해요

이 버그의 고약한 점은 **일반 컴포넌트 테스트로는 안 잡힌다**는 거예요. `mount()`로 띄우면 JS가 돌고 있으니 선택 상태가 맞게 보입니다. 통과해요. 그런데 사용자가 보는 첫 화면은 틀려 있어요.

그래서 `renderToString`으로 서버가 보내는 HTML 문자열을 직접 검사했어요.

```tsx
describe('Select 서버 렌더링', () => {
  it('SSR HTML에 선택된 option의 selected가 들어간다 (JS 실행 전에도 올바른 선택 표시)', async () => {
    const app = createSSRApp({
      render: () =>
        h(Select, {
          options,
          modelValue: 'published',
          placeholder: '선택',
          'aria-label': '상태',
        }),
    });
    const html = await renderToString(app);
    expect(html).toMatch(/<option value="published" selected>/);
    // 빈 값 option은 HTML에 value=""가 아니라 value로 출력된다
    expect(html).not.toMatch(/<option value selected>/);
  });

  it('값이 비어 있으면 placeholder option이 selected', async () => {
    const app = createSSRApp({
      render: () =>
        h(Select, { options, modelValue: '', placeholder: '선택', 'aria-label': '상태' }),
    });
    expect(await renderToString(app)).toMatch(/<option value selected>/);
  });
});
```

두 번째 테스트의 정규식이 `value=""`가 아니라 `value`인 걸 눈치채셨나요. 빈 문자열 속성은 `value=""`가 아니라 **`value`로 출력돼요.** 처음에 `value=""`로 쓰고 왜 안 맞나 한참 봤습니다. 주석으로 남겨뒀어요.

```bash
npx vitest run src/components/Select/Select.test.tsx
# ✓ 21 tests passed
```

## 접근성으로 보면

이건 "잠깐 깜빡이는 UI 버그"가 아니에요.

KWCAG·WCAG로 보면 **지금 상태를 잘못 알려주는 문제**입니다. 화면낭독기로 폼을 다시 확인할 때, JS 실행 전이라면 "전체, 선택 상자"라고 읽혀요. 실제 결과는 "채용"인데요. 눈으로 보는 사람에게도 똑같이 틀린 정보고요.

필터·정렬·페이지 크기 같은 **GET 폼으로 상태를 주고받는 선택 상자는 다 해당돼요.** 폼을 비동기로 처리하고 주소를 안 바꾸는 구조라면 안 만나는 버그라, 서버 렌더링으로 돌아가는 공공 사이트에서 더 잘 드러납니다.

## 오늘 정리

1. **`select`의 선택 상태를 HTML로 말하는 방법은 `option`의 `selected`뿐이에요.** `<select value="...">`는 브라우저가 무시합니다.
2. **`input`은 되고 `select`는 안 되는 이유**는 한쪽은 HTML 속성, 한쪽은 DOM 속성이기 때문이에요.
3. **SSR 화면의 테스트는 `renderToString`으로.** `mount()`는 JS가 돌고 있어서 이 부류의 버그를 통과시켜요.

본인 프로젝트가 SSR이라면, **JS를 끄고 필터를 한 번 써보세요.** 결과와 화면이 다른 말을 하는 곳이 있으면 거기가 같은 문제예요.
